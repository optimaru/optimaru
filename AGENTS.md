# Agent instructions

- This repository is public. Write everything in English: code, comments, docs, commit messages, PR text and review comments (the review workflows are told the same). The one exception is the Korean label and description each constraint carries next to the English ones (`label_ko`, `description_ko` in `constraints.py`): they are data for a Korean UI.
- Do not name third-party vendors or competitors, or their product menus and manual terms, in code, docs, sample data or UI text. Use neutral terms and fictional sample names. The OR-Tools comparisons (in `benchmarks/`, and where guides, docstrings and comments refer to the CP-SAT reference models and their results), the download URL of a public benchmark instance archive, the Timefold attribution required by `NOTICE`, and the origin of the bundled runtime libraries named in `THIRD-PARTY-LICENSES` and the text that points to it are the exceptions.
- Keep docs in sync with code in the same PR. A change to a use case updates its guide (`docs/use-cases/<slug>/README.md` and `python.md`), `_core.pyi` and docstrings, its notebook in `examples/`, and its `benchmarks/<slug>/` READMEs and results text when they describe the changed behavior. Engine or packaging changes update `README.md`, `docs/pypi.md` (the PyPI page), `docs/use-cases/README.md`, `docs/extending.md` and `CHANGELOG.md`. A new or newly derived directory updates the lists in `NOTICE`.
- Constraint tables (Python name, C++ component, default level and weight, flippability, rewards) must equal `<package>.constraint_info()`. Counts stated in docs (use cases, acceptors, constraints per use case) and CLI flags and defaults must equal the code; update this file too when they change what it says.
- Before finishing, grep the docs for every name you touched (functions, parameters, constraints, flags, file paths) and check each hit against the code. Run README code examples that you changed or that use what you changed.
- The CP-SAT models and their parity tests live in [external-solver](https://github.com/optimaru/external-solver). `benchmarks/<slug>/cpsat` only runs them against this checkout. School timetabling keeps its CP-SAT model in `benchmarks/school-timetabling/cpsat`. Links to files in external-solver use the tag the benchmark projects pin (`blob/v<tag>/...`, `tag` in `[tool.uv.sources]`); bump them together with the tag.
- optimaru.com documents this engine. When a change alters public API, defaults, constraint names, counts, install commands or benchmark results, say in the PR that the homepage needs an update (its `check:docs` script compares its docs data with the installed `optimaru`).
- Changing `version` in `pyproject.toml` publishes: on merge to `main`, `wheels.yml` builds the wheels, uploads them to PyPI and tags the release. Never change it unless the owner asks for a release.
- Open a PR for every change, read the claude-review comment, apply the reasonable suggestions, and merge it yourself once the latest review has nothing important left. Do not wait to ask. Releases are the owner's.
- macOS: if native builds fail to link with the default SDK, point `SDKROOT` at an older installed SDK (`ls /Library/Developer/CommandLineTools/SDKs/`; `xcrun --show-sdk-path` shows the default) for both the cmake and the `uv sync` builds.
- Layout: one Python package, `optimaru/`. The engine is header-only in `optimaru/cpp/optimaru/`; each use case is a subpackage `optimaru/<use case>/` with its C++ (`bindings.cpp`, `include/`, `src/`) in `optimaru/<use case>/cpp/`. Tests mirror the package in `tests/` (`tests/engine/`, `tests/<use case>/`, with C++ tests in `tests/<use case>/cpp/`). `setup.py` builds every subpackage that has a `_core.pyi` from its `cpp/bindings.cpp` and `cpp/src/*.cpp` except `main.cpp`; a new source file needs only a line in the use case's `CMakeLists.txt`. Python that several use cases need is written once, in the private modules next to the subpackages (`optimaru/_constraint.py`: the constraint-spec base; `optimaru/_solve.py`: the steps the `solve()` functions share; `optimaru/_models.py`: the pydantic model base, the common solver settings and the `with_initial_solution` checks); use them instead of copying into a use case.
- A new use case is a subpackage `optimaru/<use case>/` with `_core.pyi`, `cpp/` (its own `CMakeLists.txt`), `tests/<use case>/`, `docs/use-cases/<slug>/` and `benchmarks/<slug>/`, and its name in `optimaru/__init__.py` `__all__`, the root `CMakeLists.txt` `OPTIMARU_ALL_USE_CASES` and `tests/_problems.py` (the small problem the contract tests solve); `tests/test_layout.py` fails until every list has it. CI needs no line: `ci.yml` reads the use cases off the `_core.pyi` stubs.
- Formatting is checked by CI's `lint` job. Before committing: `uv run ruff check --fix . && uv run ruff format .` (Python, 120 columns) and `git ls-files -z '*.cpp' '*.hpp' | xargs -0 uv run clang-format -i` (C++; `.clang-format` is the engine's style: Google's rules, four-space indent, 100 columns). The formatter skips guides (`*.md`) and notebooks, which keep their hand layout. `pyproject.toml` at the root is the only ruff configuration; a benchmark project does not add its own (`tests/test_layout.py` checks), and a new benchmark package whose name does not end in `_cpsat` goes into its `known-first-party` list.
- C++ tests (engine and every use case): `cmake -B build && cmake --build build -j && ctest --test-dir build`; `-DOPTIMARU_USE_CASES=<use case>` (or `none`) narrows the build. Also `python3 scripts/check_license_headers.py`.
- Python tests, from the repository root: `uv sync && uv run pytest -q` (all 22 extensions), or, for one use case, `export OPTIMARU_USE_CASES=<use case>` and then `uv sync && uv run pytest -q tests/<use case>`. Keep it exported for the test run: uv rebuilds when the variable changes, and the contract tests (`tests/test_solve_contract.py`, `tests/test_solver_config_contract.py`, `tests/test_constraints_contract.py`) skip only the use cases it leaves out. uv rebuilds the in-place extensions when C++ under `optimaru/` changes; `uv sync --reinstall-package optimaru` forces it.
- Docs site: `uv run --no-project --with-requirements docs/requirements.txt mkdocs build --strict` (or `mkdocs serve`). The navigation and the API reference pages are generated by `scripts/gen_docs_pages.py`; a new page under `docs/` needs a line there. Docstrings and `_core.pyi` stubs render as Markdown, so put bracketed index expressions in backticks.
- Benchmark projects are `uv` projects (`benchmarks/<slug>/cpsat`, `benchmarks/vehicle-routing`) that install `optimaru` from this checkout; run their smoke tests with `uv run pytest -q` there (`OPTIMARU_USE_CASES=<use case>` keeps the build to one extension). Do not commit downloaded instances or raw results.
