# Agent instructions

- This repository is public. Write everything in English: code, comments, docs, commit messages and PR text.
- Do not name third-party vendors or competitors, or their product menus and manual terms, in code, docs, sample data or UI text. Use neutral terms and fictional sample names. The OR-Tools comparisons in `benchmarks/` and the Timefold attribution required by `NOTICE` are the exceptions.
- Keep docs in sync with code in the same PR. A change to a use case updates its `README.md`, `python/README.md`, `_core.pyi` and docstrings, its notebook in `examples/`, and its `benchmarks/<slug>/` READMEs and results text when they describe the changed behavior. Engine or packaging changes update `README.md`, `python/README.md` (the PyPI page), `use-cases/README.md` and `CHANGELOG.md`. A new or newly derived directory updates the lists in `NOTICE`.
- Constraint tables (Python name, C++ component, default level and weight, flippability, rewards) must equal `<package>.constraint_info()`. Counts (22 use cases, 7 acceptors, constraints per use case) and CLI flags and defaults must equal the code.
- Before finishing, grep the docs for every name you touched (functions, parameters, constraints, flags, file paths) and check each hit against the code. Run README code examples that you changed or that use what you changed.
- The CP-SAT models and their parity tests live in [external-solver](https://github.com/optimaru/external-solver). `benchmarks/<slug>/cpsat` only runs them against this checkout. School timetabling keeps its CP-SAT model in `benchmarks/school-timetabling/cpsat`. Links to files in external-solver use the tag the benchmark projects pin (`blob/v<tag>/...`, `tag` in `[tool.uv.sources]`); bump them together with the tag.
- optimaru.com documents this engine. When a change alters public API, defaults, constraint names, counts, install commands or benchmark results, say in the PR that the homepage needs an update (its `check:docs` script compares its docs data with the installed `optimaru`).
- Changing `version` in `pyproject.toml` publishes: on merge to `main`, `wheels.yml` builds the wheels, uploads them to PyPI and tags the release. Never change it unless the owner asks for a release.
- Open a PR for every change, read the claude-review comment, apply the reasonable suggestions, and merge it yourself once the latest review has nothing important left. Do not wait to ask. Releases are the owner's.
- macOS: if native builds fail to link with the default SDK, point `SDKROOT` at an older installed SDK (`ls /Library/Developer/CommandLineTools/SDKs/`; `xcrun --show-sdk-path` shows the default) for both the cmake and the `uv sync` builds.
- Engine tests: `cmake -B build && cmake --build build -j && ctest --test-dir build`. Also `python3 scripts/check_constraint_base.py --require-all` and `python3 scripts/check_license_headers.py`.
- Use-case tests: `cd use-cases/<slug>/python && uv sync --all-groups --all-extras && uv run pytest -q`. `uv sync` keeps a stale extension after C++ edits; run `uv sync --reinstall` (or `--reinstall-package <package>`) after touching `bindings.cpp`, headers or `cpp/src`.
- Benchmark projects are `uv` projects (`benchmarks/<slug>/cpsat`, `benchmarks/vehicle-routing`); run their smoke tests with `uv run pytest -q` there. Do not commit downloaded instances or raw results.
