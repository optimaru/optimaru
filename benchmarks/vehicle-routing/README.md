# Vehicle routing benchmark (CVRP and VRPTW)

The [`vehicle-routing`](../../docs/use-cases/vehicle-routing) use case against a
widely used open-source solver on the classic capacitated VRP and on the VRP
with time windows:

| Backend | Solver | Setup |
| --- | --- | --- |
| `engine` | optimaru, `optimaru.vehicle_routing` | default configuration, 1 worker |
| `ortools` | [Google OR-Tools](https://developers.google.com/optimization/routing) Routing solver (`pywrapcp`) | PATH_CHEAPEST_ARC + guided local search, the library's recommended VRP setup; on VRPTW a time dimension carries the windows, as in the library's VRPTW example |

OR-Tools lives here only; it is not part of the use case.

## Protocol (CVRP)

- **Instances**: [CVRPLIB Set X](https://galgos.inf.puc-rio.br/cvrplib/index.php/en/instances/1)
  (Uchoa et al. 2017, 100 instances, 100–1000 customers) with the current
  best-known solutions (BKS), read from the official catalog or its
  [GitHub mirror](https://github.com/PyVRP/Instances), and Augerat's Set A
  (27 instances, 31–79 customers, each file carrying its optimum), downloaded
  from CVRPLIB one file at a time, each SHA-256 pinned.
- **Same inputs**: every backend gets the same fleet, the vehicle capacity,
  and the same rounded integer distance matrix (CVRPLIB's EUC_2D rule). Routes
  are round trips from the depot.
- **Fleet**: Set A fixes the number of routes, so its fleet is the `-kN` of
  the instance name. Set X leaves it open: `-kN` there is the fewest vehicles
  that can carry the demand, and the best-known solutions of 22 of the 100
  instances use more routes than that (the mirror's solution files on
  2026-11-10). On Set X every backend therefore gets
  a fleet that cannot bind — 30% above the capacity lower bound
  (total demand / capacity), plus three (`instance.free_fleet`) — and may leave
  vehicles unused. With the fleet held at `-kN` the BKS of those 22 instances
  is out of reach for any solver.
- **Same budget**: wall-clock seconds per run (`--seconds`), same seed,
  single-threaded.
- **Independent rescoring**: the harness rebuilds each plan's distance from
  the matrix, checks capacity and that no customer appears twice, and refuses
  a backend whose own reported distance disagrees.
- **Gap** = (distance − BKS) / BKS, counted only for complete runs (every
  customer served, no route over capacity). An incomplete run is reported as
  `n unassigned` (OR-Tools may drop a customer at a penalty when it cannot
  fit it in time) or `infeasible` (a route ends over capacity).

## Protocol (VRPTW)

- **Instances**: the two instance families the VRPTW literature compares on.
  Solomon (1987, *Operations Research* 35(2)): 56 instances of 100 customers
  in six classes, clustered (C), random (R) and mixed (RC) customers, each
  with a short horizon and small vehicles (C1, R1, RC1) and with a long
  horizon and large vehicles (C2, R2, RC2). Gehring and Homberger (1999)
  extended the same six classes to 200, 400, 600, 800 and 1000 customers, ten
  instances per class and size (300 instances).
- **Scoring: the DIMACS convention**, which the 12th DIMACS Implementation
  Challenge (2021, VRPTW track) set and under which CVRPLIB lists its
  best-known solutions: the objective is total distance alone, and every
  distance, which is also the travel time, is the Euclidean distance truncated
  to one decimal. The harness keeps distances and times in tenths, so they are
  integers. The older convention of the SINTEF tables, the fewest vehicles
  first and then distance on unrounded distances, ranks other solutions first
  and is not what these gaps measure.
- **Files and best-known solutions**: read from the
  [PyVRP/Instances](https://github.com/PyVRP/Instances) GitHub repository,
  which carries all 356 instances in VRPLIB form with the CVRPLIB best-known
  solution of each, and downloaded at one pinned commit
  (`vrptw.MIRROR_COMMIT`), so an instance and its reference cannot change
  under a run. Every one of the 356 best-known solutions, rescored by the
  harness, came to its listed cost and met every window and capacity (checked
  on 2026-11-19).
- **Same inputs**: every backend gets the fleet of the file (25 vehicles on
  Solomon, 50 to 250 on Gehring & Homberger; a plan may leave vehicles
  unused), the capacity, the same integer distance matrix and the windows. A
  route leaves the depot when it opens, may wait at a customer it reaches
  early, must start each service by the end of its window and be back at the
  depot by its closing time. The engine's `max_end_time` bounds arrival plus
  service rather than the start of service, so the harness passes the end of
  each window plus the service time, which is the same condition.
- **Same budget, rescoring, gap**: as for CVRP. The rescoring also replays the
  schedule of every route, and a run that misses a window is reported as
  `infeasible`, with no gap.

## Running

Requires [uv](https://docs.astral.sh/uv/).

```sh
cd benchmarks/vehicle-routing
uv sync                                      # builds the engine's pybind extension

# one Augerat instance, all backends
uv run python -m vrp_benchmark --instance A-n32-k5 --seconds 10

# all 27 Set A instances
uv run python -m vrp_benchmark --series a --seconds 30 --out bench/set-a.json

# Set X, one median instance per size bucket
uv run python -m vrp_benchmark --series x --limit-per-bucket 1 --seconds 60 \
  --catalog-source mirror --out bench/set-x.json --summary-markdown bench/set-x.md

# all 100 Set X instances, a subset of backends
uv run python -m vrp_benchmark --series x --seconds 30 --backend engine,ortools

# chosen instances of a series
uv run python -m vrp_benchmark --series x --only X-n101-k25 --only X-n153-k22 --seconds 30

# VRPTW: all 56 Solomon instances, three runs side by side
uv run python -m vrp_benchmark --series solomon --seconds 30 --jobs 3 --out bench/vrptw-solomon.json

# Gehring & Homberger: one instance per class and size (30), or all 300
uv run python -m vrp_benchmark --series homberger --limit-per-bucket 1 --seconds 30 --jobs 3
uv run python -m vrp_benchmark --series homberger --seconds 30 --jobs 3 --out bench/vrptw-homberger.json
```

`--jobs N` runs N single-threaded runs at a time in separate processes. Keep
it below the number of cores, since a run that waits for a core loses search
time; the JSON records it (`protocol.jobs`).

`uv run pytest` checks the parsers, the rescoring (time windows included) and
that every backend finds the optimum of a tiny CVRP and a tiny VRPTW instance.

The [`vrp-public-bench`](../../.github/workflows/vrp-public-bench.yml)
workflow, run by hand (Actions > vrp-public-bench > Run workflow, 15 to 20
minutes), runs the one-per-bucket sample at 60 s by default. It
posts the Markdown table as the job summary and keeps the JSON as an
artifact. It is a report, not a quality gate — gaps move with the runner —
except that an incomplete engine plan fails the job (`--fail-on-incomplete`).

## Layout

```
vrp_benchmark/
├── run.py              CLI, series runner, summaries (python -m vrp_benchmark)
├── instance.py         CVRPLIB parser, Augerat Set A download, rescore()
├── cvrplib.py          Set X catalog + BKS download and cache
├── vrptw.py            Solomon and Gehring & Homberger: VRPLIB parser, DIMACS distances, download
└── solvers/
    ├── engine.py           optimaru via optimaru.vehicle_routing
    └── ortools_routing.py  OR-Tools Routing solver
tests/
```
